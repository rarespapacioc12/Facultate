Capitolul 01 · Curs 1 & 10 · cerut la examen: 2025/XI, 2025/III, 2025/X

Pointeri, referințe și const

Un pointer este o variabilă care reține o adresă de memorie. Pointerul are un tip: compilatorul știe ce fel de date se află la adresa respectivă, iar aritmetica de pointeri ține cont de acest tip — p++ avansează cu sizeof(tip) octeți, nu cu 1.

int i = 7, *j;   // j este pointer la int
j = &i;          // & = operatorul de adresă
*j = 9;          // * = dereferențiere: modifică valoarea de la adresa j, deci i devine 9

O referință este un alias (un alt nume) pentru o variabilă deja existentă. Spre deosebire de pointer: trebuie obligatoriu inițializată la declarare, nu poate fi „mutată" ulterior către altă variabilă și nu există referință nulă. O funcție care întoarce o referință poate apărea în stânga unei atribuiri — dar nu trebuie să întoarcă niciodată referință la o variabilă locală (aceasta dispare la ieșirea din funcție).

Regula de citire: se citește declarația de la dreapta la stânga.

Subiect 2025 · problema III (verificat cu g++)
int a = 5;
int b = ++a;              // a devine 6, b = 6
const int *a_ptr = &a;    // pointer la int CONSTANT
int *const b_ptr = &b;    // pointer CONSTANT la int
*b_ptr += 2;              // OK: valoarea pointată nu e const
*a_ptr += 3;              // EROARE: assignment of read-only location '*a_ptr'

Programul de mai sus nu compilează — corectarea cu o singură linie: se elimină linia cu *a_ptr += 3; sau se declară int *a_ptr = &a;.

Conversii între pointeri: conversia T* → const T* este implicită (adăugăm o restricție, e sigur). Conversia inversă, const T* → T*, este interzisă implicit (am scăpa de restricție). Între pointeri la tipuri diferite nu există conversii implicite (cu excepția derivată → bază, vezi cap. 06).

Alocare dinamică: new / delete

  • int *p = new int(5); — alocă un int inițializat cu 5 (paranteze rotunde = valoare inițială).
  • int *v = new int[5]; — alocă un vector de 5 int (paranteze pătrate = dimensiune).
  • Eliberarea trebuie să fie pereche: delete p; respectiv delete[] v;. Amestecarea lor (delete pe ceva alocat cu new[]) este comportament nedefinit.
  • new apelează constructorul, delete apelează destructorul (diferență esențială față de malloc/free, care doar alocă/eliberează octeți).
  • La new Tip[n] elementele se construiesc cu constructorul fără parametri — de aici capcana clasică de la examen cu doi constructori „impliciți" ambigui (vezi cap. 03).

Sintaxă: poziția lui const față de * decide ce este constant; declarațiile se citesc de la dreapta la stânga. const int* p / int const* p = pointer la întreg constant: valoarea pointată nu poate fi modificată prin p, dar pointerul poate primi altă adresă. int* const p = &x = pointer constant: adresa e fixă (obligatoriu inițializat la declarare), dar valoarea pointată se poate modifica. const int* const p = ambele constante.

Proprietăți / particularități: un T* se convertește implicit la const T*, invers nu; printr-un pointer la const se pot apela doar metode const ale obiectului pointat; parametrii de tip const T* (sau const T&) documentează și garantează că funcția nu modifică argumentul.

Exemplu: int d=1; int* const w=&d; *w=9; // OK dar w=&alt; // eroare; respectiv const int* u=&d; *u=9; // eroare.

⚠ Capcane de examen

  • Copierea unui șir cu \0 în interior se oprește la \0 (2025/X).
  • int b = ++a; — pre-incrementarea modifică întâi pe a, apoi atribuie.
  • Referința trebuie inițializată; int &r; singur nu compilează.
Capitolul 02 · Curs 2–3

Principiile OOP · clase, struct, union, friend, inline

Cele patru principii ale programării orientate pe obiecte:

  • Abstractizarea — modelăm entități reale prin tipuri de date care expun doar ce este esențial.
  • Încapsularea — datele (de regulă private) sunt ascunse, iar accesul se face printr-o interfață publică de metode (getteri/setteri); obiectul își controlează singur starea.
  • Moștenirea — crearea de tipuri noi pornind de la tipuri existente, cu reutilizare de cod (cap. 06).
  • Polimorfismul — același apel se comportă diferit în funcție de tipul real al obiectului (static: supraîncărcare; dinamic: funcții virtuale, cap. 07).

class vs struct vs union

  • Într-un struct accesul implicit este public; într-o class este private. Aceeași diferență apare și la moștenire: struct D : B moștenește implicit public, class D : B moștenește implicit private. În rest, în C++ un struct poate avea metode, constructori, moșteniri — exact ca o clasă.
  • Un union este o „clasă" în care toți membrii împart aceeași zonă de memorie (dimensiunea = cel mai mare membru). Poate avea constructori, destructor și metode, dar nu poate avea funcții virtuale, nu poate moșteni și nu poate fi moștenit.
  • Union anonim: un union fără nume și fără obiect declarat; membrii lui se folosesc direct ca variabile obișnuite (care își suprapun memoria).

Funcții și clase friend

O funcție friend a unei clase este o funcție externă (nu este metodă, nu are this) căreia clasa îi acordă acces la membrii săi private și protected. Declarația friend se scrie în interiorul clasei (în orice zonă de acces), dar funcția rămâne globală. O funcție poate fi friend pentru mai multe clase simultan (util când lucrează cu interiorul ambelor). O clasă friend: friend class B; — toate metodele lui B au acces la membrii clasei curente.

⚠ Proprietățile lui friend (întrebare clasică)
  • Nu este reciprocă: dacă A îl declară pe B friend, A nu primește automat acces în B.
  • Nu este tranzitivă: prietenul prietenului meu nu e prietenul meu.
  • Nu se moștenește: derivata lui B nu primește prietenia acordată lui B.

Funcții inline

inline este o cerere către compilator de a înlocui apelul funcției cu corpul ei (se elimină costul apelului; potrivit pentru funcții foarte scurte). Două forme:

  • explicit: inline int f(int x) { ... };
  • implicit: orice metodă definită în corpul clasei este automat inline.

Compilatorul poate ignora cererea (de exemplu pentru funcții recursive sau prea mari).

class Punct {
    int x, y;                       // private implicit
public:
    Punct(int a, int b) : x(a), y(b) {}
    int getX() const { return x; }  // definită în clasă => implicit inline
    friend double dist(const Punct&, const Punct&);  // funcție externă cu acces la x,y
};
Capitolul 03 · Curs 3 · cerut la examen: 2025/II (copy constructor)

Constructori și destructori · constructorul de copiere

Constructorul poartă numele clasei, nu are tip de retur (nici măcar void), se apelează automat la crearea obiectului și poate fi supraîncărcat. Destructorul — ~Clasa() — nu are parametri și nu poate fi supraîncărcat (unul singur per clasă); se apelează automat la distrugerea obiectului (ieșirea din domeniu pentru obiecte automate, delete pentru cele dinamice).

  • Dacă nu scriem niciun constructor, compilatorul generează unul implicit, fără parametri. Dacă scriem orice constructor, cel implicit nu se mai generează.
  • Lista de inițializare — Cls(int i) : x(i), y(0) { } — inițializează membrii înainte de corpul constructorului. Este obligatorie pentru: membri const, membri referință, subobiecte (componente / baze) fără constructor implicit.
  • Ordinea de inițializare a membrilor este ordinea declarării lor în clasă, nu ordinea din lista de inițializare!
  • Obiectele dintr-un tablou new Cls[n] se construiesc cu constructorul fără parametri; la distrugerea programului / delete[], destructorii se apelează în ordine inversă construirii.
Subiect 2024 · doi constructori „impliciți" = ambiguitate
class cls {
    int x;
public:
    cls(int i = 1) { x = i; }   // poate fi apelat și FĂRĂ argumente
    cls() : x(-1) { }           // tot fără argumente
    ...
};
cls *p = new cls[10];           // EROARE: apel ambiguu al constructorului implicit

Ambii constructori pot fi apelați fără argumente, deci orice construcție implicită (inclusiv cls a;) este ambiguă → nu compilează. Corectare pe o singură linie: se elimină unul dintre ei sau se scoate valoarea implicită = 1.

Constructorul de copiere (copy constructor)

Are forma Cls(const Cls& sursa) — parametrul este obligatoriu referință (dacă ar fi prin valoare, transmiterea parametrului ar cere... tot constructorul de copiere → recursie infinită; compilatorul respinge Cls(Cls)), de regulă const. Se apelează automat în trei situații:

  1. la inițializarea unui obiect cu un altul: Cls b = a; sau Cls b(a);
  2. la transmiterea unui obiect prin valoare ca parametru de funcție;
  3. la returnarea unui obiect prin valoare dintr-o funcție (compilatoarele moderne pot elimina copia — RVO — dar la examen se consideră modelul clasic).

Dacă programatorul nu îl definește, compilatorul generează unul implicit care copiază membru cu membru (copiere superficială / „shallow copy"). Pentru clase care dețin resurse prin pointeri (memorie alocată dinamic, fișiere), copierea superficială duce la doi pointeri către aceeași zonă → la distrugere, dublă dealocare și comportament nedefinit. Soluția: copy constructor scris de programator care face copiere profundă (alocă memorie nouă și copiază conținutul).

Copiere profundă + regula celor trei
class D : public B {
    int* d;
public:
    D(int p)           { d = new int; *d = p; }
    D(const D& s) : B(s) { d = new int; *d = *(s.d); }  // deep copy
    ~D()               { delete d; }
    D& operator=(const D& s) {              // lipsea în Subiect 2025/XII!
        if (this != &s) { B::operator=(s); *d = *(s.d); }
        return *this;
    }
};

Regula celor trei (Rule of Three): dacă o clasă are nevoie de unul dintre destructor, copy constructor, operator=, aproape sigur are nevoie de toate trei. În problema XII din 2025, clasa avea copy constructor și destructor, dar o1 = o2; folosea operator= generat implicit (copiere superficială a pointerului) → ambele obiecte ajung să pointeze aceeași zonă → la final, delete de două ori pe aceeași adresă.

📋 Răspuns model · „Definirea copy-constructorului de către programator" (2025/II)

Sintaxă: Cls(const Cls& obj) { ... } — constructor cu un singur parametru, referință (eventual const) la un obiect de același tip.

Proprietăți: este apelat automat la (1) inițializarea unui obiect dintr-altul, (2) transmiterea prin valoare către funcții, (3) întoarcerea prin valoare din funcții. Dacă nu este definit, compilatorul generează unul care copiază membru cu membru (shallow copy).

Particularități: parametrul trebuie să fie referință — prin valoare ar produce un apel recursiv infinit (transmiterea prin valoare necesită ea însăși copierea). Referința este de regulă const pentru a accepta și obiecte constante/temporare.

Motivație: necesar când obiectul deține resurse prin pointeri — copierea implicită ar duplica doar adresa, nu conținutul → modificări „prin alias" și dublă dealocare la destructori. Programatorul implementează copierea profundă; se leagă de Regula celor trei (destructor + copy ctor + operator=).

Subiect 2024 · vector<SimpleClass> și push_back — C / CC / D
class SimpleClass {
    int m;
public:
    SimpleClass(int i = 0)        { cout << "C\n";  m = i; }
    SimpleClass(const SimpleClass&) { cout << "CC\n"; }
    ~SimpleClass()                { cout << "D\n";  }

Explicație: push_back(i) cu i de tip int folosește conversia implicită dată de constructorul SimpleClass(int) → se creează un temporar (C), care este copiat în vector (CC), apoi temporarul moare (D). La a doua iterație: temporar (C), copiat (CC), dar vectorul se realocă → elementul vechi este copiat în noua zonă (CC), apoi se distrug elementul din zona veche și temporarul (D, D). La finalul lui main, cele două elemente din vector se distrug (D, D).

class Cls {

  • La return: obiectele automate din main se distrug în ordine inversă (E, apoi D).

  • O componentă (membru obiect) fără constructor implicit trebuie inițializată în lista de inițializare (2024/XVI).
  • operator= generat implicit copiază pointerii ca atare → dublă dealocare (2025/XII).

Capitolul 04 · Curs 4 & 10 · cerut la examen: metode statice (2024), ctor protected/private (2025/XIV), statice & MI (2025/XVII), max N obiecte (2024)

Membri statici · obiecte const · mutable · constructori privați

Câmpuri statice

  • Un câmp static aparține clasei, nu obiectelor: există o singură copie, partajată de toate instanțele (există chiar dacă nu există niciun obiect).
  • Declarat în clasă, dar definit (și de regulă inițializat) obligatoriu în afara clasei: int A::x = 5; — fără static la definiție. Aceasta rezervă efectiv memoria.
  • Acces: Clasa::x sau prin orice obiect (a.x).
  • Utilizare tipică: contor de instanțe — incrementat în constructori, decrementat în destructor.

Metode statice

  • Se declară cu static în clasă; nu primesc pointerul this — nu sunt asociate unui obiect anume.
  • Pot accesa direct doar membrii statici ai clasei; pentru membri nestatici ar avea nevoie de un obiect explicit.
  • Pot fi apelate fără niciun obiect: Clasa::f() (dar și prin obiect: a.f()).
  • Nu pot fi const (nu au this de „protejat") și nu pot fi virtual (legarea virtuală presupune un obiect).
Subiect 2025 · XIII — contor static de instanțieri (verificat: compilează)
class C {
    int a;
    static int x;
public:
    C(int a = 11) { x++; this->a = a; }   // this->a = parametrul ascunde membrul
    static int f() { return x; }
    int getA() { return a; }
} a;                                       // obiect GLOBAL a (folosește a=11) → x devine 11
int C::x = 10;
int main() {
    C a(55), b;                            // x devine 12, apoi 13
    cout << "instantieri C: " << C::f() << " val elem:" << ::a.getA();
}
instantieri C: 13 val elem:11

Detalii: ::a este operatorul de rezoluție aplicat global — desemnează obiectul global a (construit cu valoarea implicită 11), nu pe cel local din main. Inițializarea int C::x = 10; cu o constantă are loc înaintea construcției obiectelor globale.

Subiect 2024 · IV — pointer static partajat: (++(*x))--
class A {
    static int *x;
public:
    int get_x() { return (++(*x))--; }
};
int *A::x(new int(20));
int main() {
    A *p = new A, b;
    cout << b.get_x() << " " << p->get_x();
}
21 21

++(*x) incrementează la 21 și întoarce un lvalue; post-decrementul -- întoarce valoarea curentă (21) și readuce *x la 20. Ambele obiecte văd același x static → de două ori 21.

📋 Răspuns model · „Metodă statică vs nestatică" (2024/VIII & XIV)
  • 0.1pSintaxă: metoda statică se declară cu static în clasă; cea nestatică, fără.
  • 0.1pObiectul implicit: metodele nestatice primesc pointerul ascuns this către obiectul prin care sunt apelate; metodele statice nu au this.
  • 0.1pAcces: metodele statice accesează direct doar membrii statici ai clasei; metodele nestatice accesează atât membri nestatici cât și statici.
  • 0.1pApel: metodele statice pot fi apelate în lipsa oricărui obiect (Clasa::f()); cele nestatice au nevoie de un obiect (ob.f(), p->f()).
  • Bonus: metodele statice nu pot fi virtual și nu pot fi const.
📋 Răspuns model · „Metode statice la moștenirea multiplă" (2025/XVII)

Toate proprietățile de mai sus, plus: metodele statice se moștenesc ca orice membru, iar apelul lor se poate califica: Derivata::f() sau Baza::f(). La moștenirea multiplă, dacă două clase de bază oferă o metodă statică cu același nume, apelul nemodificat D::f() / ob.f() este ambiguu — se rezolvă calificând explicit clasa: B1::f() sau ob.B1::f(). Pentru câmpurile statice moștenite pe două căi (rombul fără virtual), există totuși o singură copie a câmpului static — staticele nu se duplică odată cu subobiectele. Metodele statice nu pot fi virtuale, deci nu participă la polimorfism.

Obiecte constante și metode const · mutable

  • O metodă const — int get() const { ... } — promite că nu modifică obiectul; în interiorul ei, this este pointer la obiect constant, deci toți membrii sunt văzuți ca const.
  • Pe un obiect const (sau printr-un pointer/referință la const) se pot apela doar metode const.
  • Capcana din 2025/IX: int& get() const { return c; } nu compilează — în metoda const, membrul c e const int, care nu se poate lega la int&. Corectare: tipul de retur devine int (prin valoare) sau const int&, ori se elimină const.
  • mutable pe un câmp permite modificarea lui chiar și din metode const / pe obiecte const (folosit pentru cache-uri, contoare de accesări).

Constructori protected / private · clase cu număr limitat de obiecte

Un constructor poate sta în orice zonă de acces. Dacă este private, obiectele nu pot fi create din exteriorul clasei — doar metodele clasei (de regulă statice, fiindcă nu au nevoie de un obiect preexistent) sau funcțiile/clasele friend pot construi instanțe. Dacă este protected, în plus pot construi și clasele derivate (clasa devine practic instanțiabilă doar ca bază — „abstractă fără funcții pure virtuale").

Singleton — cel mult UN obiect
class Singleton {
    static Singleton* inst;          // unica instanță
    Singleton() { }                  // constructor PRIVAT
public:
    static Singleton* getInstance() {            // funcție STATICĂ
        if (inst == nullptr) inst = new Singleton();  // alocare DINAMICĂ, o singură dată
        return inst;
    }
};
Singleton* Singleton::inst = nullptr;
Generalizare — cel mult N obiecte (la examen: N = 2 sau 3)
class MaxN {
    static int cate;                 // contor de instanțe existente
    MaxN() { cate++; }               // constructor privat
public:
    static MaxN* creeaza() {
        if (cate >= 3) return nullptr;   // refuză peste limită
        return new MaxN();
    }
    ~MaxN() { cate--; }              // eliberează un „loc"
};
int MaxN::cate = 0;
📋 Răspuns model · „Clasă cu cel mult N obiecte" (2024/XIV & VIII) și „constructor protected/private" (2025/XIV)

Ingredientele punctate de barem: ctor privat împiedică instanțierea liberă; funcție statică este singura poartă de creare (poate fi apelată fără obiect); alocare dinamică obiectul se creează cu new în interiorul funcției statice; un câmp static contor numără instanțele și funcția refuză (întoarce nullptr) când s-a atins limita N. Destructorul decrementează contorul. Caz particular: N=1 → Singleton; N=0 → clasă abstractă (sau toți constructorii privați și nicio funcție de creare).

Pentru constructor protected: clasa nu poate fi instanțiată direct, dar derivatele îl pot apela din constructorii lor → șablon de „clasă de bază obligatorie". Pentru ambele: friend-urile pot construi; util la Singleton, Factory, clase utilitare fără instanțe.

⚠ Capcane de examen
  • Câmpul static nedefinit în afara clasei → eroare de linker la folosire.
  • static + virtual pe aceeași metodă → nu compilează.
  • Clasele locale (definite în funcții) nu pot avea câmpuri statice; clasele imbricate (nested) pot.
  • Returnarea unui int& către un membru dintr-o metodă const → eroare (2025/IX).
  • Obiectele statice locale se construiesc la primul apel al funcției, o singură dată (2025/IV).
Capitolul 05 · Curs 4–5 · cerut la examen: 2024/I & XII, 2025/VI & XVIII (name hiding pe operatori și metode)

Supraîncărcarea funcțiilor și a operatorilor

Supraîncărcarea funcțiilor (overloading)

  • Mai multe funcții pot avea același nume dacă diferă prin lista de parametri (număr sau tipuri). Tipul returnat nu participă la diferențiere.
  • Compilatorul alege varianta prin rezoluția supraîncărcării: potrivire exactă > promovări (char→int) > conversii standard (int→double) > conversii definite de utilizator.
  • Parametrii cu valori implicite pot crea ambiguități: f(int i=1) și f() intră în conflict la apelul f() — exact ambiguitatea celor doi constructori din 2024/III & IV (vector de obiecte ⇒ se cere constructorul fără argumente, care e ambiguu).

Supraîncărcarea operatorilor — reguli generale

  • Se face printr-o funcție cu numele operatorXX. Nu se pot crea operatori noi, nu se schimbă aritatea, precedența sau asociativitatea.
  • Nu pot fi supraîncărcați: ::, ., .*, ?:, sizeof, typeid.
  • Doar ca metode membre (nu friend/globale): =, [], (), ->.
  • Cel puțin un operand trebuie să fie de tip clasă (nu poți redefini int + int).

Name hiding — capcana clasică de examen (2024/I, 2025/XVIII, 2025/VI)

Dacă derivata definește o funcție cu același nume ca în bază (indiferent de semnătură!), toate supraîncărcările din bază cu acel nume devin ascunse. Căutarea numelui se oprește la primul domeniu care îl conține — nu se „combină" listele de supraîncărcări din bază și derivată.

class Base {
public:
    int f() const { cout << "B1\n"; return 1; }
    int f(string) const { cout << "B2\n"; return 1; }
};
class Derived : public Base {
public:
    int f() const { cout << "D1\n"; return 2; }   // ascunde AMBELE f() din Base
};
int main() {
    string s("hello");
    Derived d;
    int x = d.f();      // OK: D1
    d.f(s);             // EROARE: Derived::f nu primește string; Base::f(string) e ascuns
}
eroare de compilare la d.f(s) — „no matching function for call to f(string)"

Reparații acceptate de barem: se elimină linia cu d.f(s), sau d se declară de tip Base, sau se apelează calificat d.Base::f(s), sau se aduce explicit în derivată: using Base::f;.

Compunere vs moștenire · controlul accesului

Definiții

  • Compunerea („has-a"): o clasă conține obiecte ale altor clase drept câmpuri (subcomponente). Ex.: Mașina are un Motor.
  • Moștenirea („is-a"): o clasă derivată preia interfața și implementarea unei clase de bază și o extinde/specializează: class Derivata : public Baza { };. Ex.: Studentul este o Persoană.
📋 Răspuns model · „Compunere vs moștenire" (2024/XI, V2/II) — pe punctele de barem

0.1 definiție compunere Compunerea = relația „are-un": clasa conține ca membri obiecte ale altor clase (subcomponente), care există doar prin intermediul obiectului-container.

0.1 definiție moștenire Moștenirea = relația „este-un": clasa derivată preia membrii clasei de bază (class D : public B) și poate adăuga sau redefini comportament.

0.1 lista de inițializare Atât subcomponentele cât și subobiectul de bază se construiesc prin lista de inițializare a constructorului: D(int x, int y) : B(x), comp(y) { }. Fără apel explicit, compilatorul cheamă constructorul fără parametri al bazei/componentei — dacă acesta nu există, eroare (2024/XVI).

0.1 drepturi de acces Diferență esențială: containerul accesează din subcomponente doar membrii publici; derivata accesează din bază membrii publici și protected (nu și pe cei privați).

0.1 conversii Conversia derivată → bază este implicită (upcasting: Baza* p = new Derivata;). Conversia container → componentă nu există implicit; se scrie explicit, supraîncărcând operatorul cast: operator Motor() const { return motor; }.

Ordinea construcției și distrugerii

  • La crearea unui obiect derivat: 1) constructorul bazei (bazelor, în ordinea declarării la moștenire), 2) constructorii membrilor/subcomponentelor în ordinea declarării în clasă (nu ordinea din lista de inițializare!), 3) corpul constructorului derivatei.
  • Destructorii se apelează exact invers: corp derivată → membri (invers) → bază.

Eroarea clasică: subcomponentă fără constructor implicit (2024/XVI & V2/XV)

class A {
    int i;
public: A(int x):i(x) { }          // NU există A()
    int get_i() { return i; } };
class B {
    A a;                            // subcomponentă
    int j;
public: B(int x, A y) { j=x; a=y; }  // EROARE: înainte de corp, B trebuie să construiască a
};                                   //          → caută A() inexistent
int main() { A o1(5); B o2(6,o1); cout<<o1.get_i()<<o2.get_j(); }
eroare de compilare · reparația de barem: linia constructorului devine B(int x, A y) : a(y) { j=x; } — apelul a(y) în lista de inițializare

Capitolul 07 · Curs 6–7 · teorie: „virtual" (2024/II & XI), „destructor virtual pur" (2025/V) · programe: 2024/VI & V2-I, 2024/VII & V2-XII, 2025/XVI

Funcții virtuale · clase abstracte · destructori virtuali

Mecanismul funcțiilor virtuale

  • O metodă declarată virtual în bază și redefinită cu aceeași semnătură în derivată se apelează prin legare dinamică (late binding): printr-un Baza* sau Baza& către un obiect derivat se execută versiunea derivatei.
  • Implementare: fiecare clasă cu metode virtuale are o tabelă virtuală (vtable); fiecare obiect poartă un pointer ascuns (vptr) către ea. La apel, funcția se alege la rulare după tipul real al obiectului — pe asta se bazează și RTTI (cap. 09).
  • virtual se scrie o dată în bază; în derivate redefinirea rămâne automat virtuală (C++11: marcăm cu override ca să prindă greșelile de semnătură).
class B { int i;
public: B() { i=50; }
    virtual int get_i() { return i; } };
class D: public B { int j;
public: D() { j=47; }
    int get_j() { return j; } };
int main() {
    B *p = new D;          // upcast implicit, corect
    cout << p->get_i();    // virtual → dar D nu redefinește → B::get_i → 50
}
📋 Răspuns model · „Folosirea cuvântului cheie virtual" (2024/II & V2-XI) — pe punctele de barem

0.1 funcții virtuale virtual declară funcții virtuale — metode redefinibile în derivate, apelate prin legare dinamică.

0.1 pointer bază → obiect derivat Utilizare tipică: Baza* p = new Derivata; — apelul p->f() execută Derivata::f() dacă f e virtuală, deși tipul static al lui p e Baza*.

0.1 sintaxă + RTTI Sintaxă: virtual tip f(...); în bază (eventual = 0 pentru pur). Alegerea funcției se face la execuție pe baza informației de tip de la rulare (RTTI/vtable), nu la compilare.

0.1 problema rombului virtual apare și la moștenire: class D : virtual public B rezolvă problema rombului din moștenirea multiplă — baza comună apare o singură dată.

0.1 virtual pe ambele ramuri Ca să se evite ambiguitatea/duplicarea la romb, moștenirea virtuală trebuie pusă pe ambele ramuri intermediare (cap. 08).

Erori tipice de examen în jurul lui virtual

// 2024/VI & V2-I — direcția pointerului
D *p = new B;        // EROARE: un D* nu poate pointa către un obiect Base
                     // reparare (linia 12): D *p = new D;   (sau B *p = new B;)

// 2024/VII & V2-XII — „override" cu ALTĂ semnătură = ascundere, nu redefinire
class X { public: virtual void Print(A *a) { ... } };
class Y: public X { public: void Print(B *b) { ... } };  // alt parametru!
Y* yptr = new Y;
yptr->Print(aptr);   // aptr e A* → EROARE: Y::Print cere B*, X::Print(A*) e ascuns
                     // reparare: în Y, parametrul devine A* (override real)

Regulă: redefinirea virtuală cere semnătură identică (excepție: tipul de retur covariant, mai jos). Cu altă listă de parametri obținem name hiding (cap. 05), nu polimorfism.

Funcții pur virtuale și clase abstracte

  • virtual void f() = 0; — funcție pur virtuală: fără implementare obligatorie; clasa devine abstractă — nu poate fi instanțiată, servește ca interfață.
  • Derivata trebuie să implementeze toate funcțiile pur virtuale, altfel rămâne și ea abstractă.
  • Se pot declara pointeri și referințe la clase abstracte (baza polimorfismului): Forma* f = new Cerc;.
  • O funcție pur virtuală poate avea corp (definit în afara clasei) — apelabil calificat: Forma::f().

Destructori virtuali · destructor virtual pur (2025/V)

class B { public: virtual ~B() { cout << "~B "; } };
class D : public B { int* p;
public: D() { p = new int[10]; }
    ~D() { delete[] p; cout << "~D "; } };
int main() {
    B* b = new D;
    delete b;        // virtual: ~D apoi ~B. FĂRĂ virtual: doar ~B → memory leak!
}
~D ~B
📋 Răspuns model · „Destructor virtual pur" (2025/V)

Sintaxă: virtual ~C() = 0; în clasă, plus — obligatoriu — o definiție cu corp în afara clasei: C::~C() { }. Proprietăți: (1) clasa devine abstractă chiar dacă nu are alte funcții pure — truc folosit când vrem să interzicem instanțierea dar nu avem altă metodă de făcut pură; (2) corpul este necesar pentru că destructorul derivatei apelează automat destructorul bazei (destructorii se înlănțuie, nu se „suprascriu" ca celelalte virtuale) — fără corp, eroare la link; (3) fiind virtual, garantează distrugerea corectă (întâi derivata, apoi baza) la delete printr-un pointer de bază. Motivație: clase de bază polimorfice care trebuie să fie abstracte; orice clasă cu măcar o funcție virtuală ar trebui să aibă destructor virtual.

  • Constructorii nu pot fi virtuali (obiectul nu există încă; vptr-ul se setează în constructor). În interiorul unui constructor/destructor, apelurile la funcții virtuale se rezolvă static, la nivelul clasei curente.
  • static + virtual = combinație interzisă (metodele statice nu au this, deci nici vptr).

Tip de retur covariant (2025/XVI)

class B { public:
    virtual B* fv() { return this; }
    int adun(int p) { return p + 1; } };
class D : public B { public:
    virtual D* fv() { return this; }     // OK: D* e covariant cu B*
    int adun(int p) { return p + 2; } }; // NE-virtual → ascunde, nu redefinește
int main() {
    B* p = new D;
    int x = p->fv()->adun(5);
    cout << x;          // fv() dinamic → D::fv, DAR tipul static returnat e B*
}                       // → adun = B::adun → 5+1
6

Redefinirea virtuală poate schimba tipul de retur doar în pointer/referință la o clasă derivată din tipul original (covariant). Atenție: expresia p->fv() are tipul static B*, deci ce urmează după ea se leagă static — adun nefiind virtual, se ia B::adun → 6.

⚠ Capcane de examen
  • D *p = new B; nu compilează niciodată (downcast implicit inexistent) — 2024/VI.
  • Apel virtual ≠ magie: dacă derivata nu redefinește, se execută versiunea bazei (50 în exemplul B/D).
  • ((D*)p)->get_j() pe un obiect care chiar e D → merge (21 21 / 4 4 la 2024/I & V2-III prin câmpul static); pe un obiect care e doar B → comportament nedefinit, dar la examen întrebarea e de compilare.
  • Funcțiile virtuale nu pot fi static; pot fi const; constructor virtual nu există, destructor virtual da (și recomandat).
Capitolul 08 · Curs 7 · cerut la examen: 2025/I (romb, ordinea ctor/dtor), 2025/XV (ambiguitate), teoria „virtual pe ambele ramuri" (2024/II)

Moștenirea multiplă · problema rombului

Sintaxă și ambiguități

class D : public B1, protected B2 { ... };   // mai multe baze, fiecare cu specificatorul ei
  • Derivata conține câte un subobiect pentru fiecare bază; constructorii bazelor se apelează în ordinea declarării la moștenire (nu ordinea din lista de inițializare).
  • Dacă două baze au membri cu același nume, accesul nesimplificat e ambiguu → se califică: ob.B1::f().

Problema rombului (diamond)

      Baza                 class Derivata1 : virtual public Baza { };
     /    \                class Derivata2 : virtual public Baza { };
 Derivata1  Derivata2      class Finala : public Derivata1, public Derivata2 { };
     \    /
     Finala     // fără virtual: Finala ar conține DOUĂ copii ale Bazei → ambiguitate la orice membru
  • Cu moștenire virtuală pe ambele ramuri, baza comună apare o singură dată — exact punctul de barem de la întrebarea „virtual" (2024/II).
  • Cine construiește baza virtuală? Clasa cea mai derivată (cea instanțiată) apelează direct constructorul bazei virtuale; apelurile din clasele intermediare se ignoră. Dacă nu apare în listă, se folosește constructorul implicit al bazei.
  • Ordinea construcției la moștenire multiplă: 1) toate bazele virtuale (o singură dată, în ordinea apariției în ierarhie), 2) bazele nevirtuale în ordinea declarării, 3) membrii, 4) corpul constructorului. Destructorii: invers.

Subiectul 2025/I — trasare completă (verificat prin compilare)

class Baza{ public: Baza(){cout<<"CoB\n";} };

        ~Derivata1(){cout<<"DD1\n";}  };

        virtual ~Derivata2(){cout<<"DD2\n";} };

De ce: programul compilează (DA). Construcția lui Derivata5: întâi baza virtuală Baza de pe ramura Derivata3 → primul „CoB". Apoi bazele nevirtuale în ordinea declarării: Derivata1 (Baza proprie „CoB" + „CoD1"), Derivata2 („CoB" + „CoD2"), Derivata3 (baza ei virtuală e deja construită → doar „CoD3"), Derivata4 (Baza proprie „CoB" + corpul constructorului care afișează — capcană! — „DD4"), apoi corpul lui Derivata5 („CoD5"). La distrugere, invers, dar doar ~Derivata2 și ~Derivata1 afișează ceva: „DD2", „DD1". Capcana dublă: Derivata4 nu are destructor (mesajul „DD4" vine din constructor), iar Derivata2 e moștenită privat (fără specificator la class) — irelevant pentru output.

Pentru ob2(20): clasa cea mai derivată apelează direct I(20) („20ci"), apelurile I(x) din uni/oras se ignoră, iar uni și oras se construiesc cu constructorii impliciți („CU", „CO"); corpul lui unibuc(int) nu afișează nimic.

⚠ Capcane de examen
  • Bazele virtuale se construiesc înaintea tuturor celorlalte baze, indiferent de poziția în declarație.
  • Apelurile I(x) din constructorii claselor intermediare se ignoră când clasa nu e cea mai derivată.
  • Fără specificator, class D : B moștenește privat — în 2025/I, Derivata2 e bază privată (nu schimbă outputul, dar poate apărea ca întrebare).
  • Mesajele afișate de constructori/destructori se citesc cu atenție — „DD4" din constructor e capcana clasică.
  • virtual doar pe o ramură nu rezolvă rombul: rămân două subobiecte (unul virtual, unul nu).
Capitolul 09 · Curs 7–8 · întrebare de teorie: typeid (2025/VIII)

RTTI: typeid și operatorii de cast

typeid

  • Necesită #include <typeinfo>. Expresia typeid(expr) sau typeid(Tip) returnează o referință constantă la un obiect const type_info&.
  • Pe tipuri nepolimorfice se evaluează la compilare (tipul static). Pe expresii de tip polimorfic (clasa are măcar o funcție virtuală), se evaluează la rulare și întoarce tipul real al obiectului — acesta este RTTI (Run-Time Type Information), bazat pe vtable.
  • type_info oferă operator==, operator!= și name() (numele e implementation-defined — g++ returnează nume „mangled", de ex. 1D; compararea corectă se face cu ==, nu cu name()=="D").
class B { public: virtual void f() {} };   // polimorfică
class D : public B { };
int main() {
    B* p = new D;
    cout << (typeid(*p) == typeid(D));   // 1 — tipul REAL al obiectului
    cout << (typeid(p)  == typeid(B*));  // 1 — pointerul însuși NU e polimorfic
    B* q = nullptr;
    typeid(*q);                          // aruncă excepția std::bad_typeid
}
📋 Răspuns model · „Particularitățile operatorului typeid" (2025/VIII)

Sintaxă: typeid(expresie) / typeid(Tip), cu #include <typeinfo>; întoarce const std::type_info&. Proprietăți: obiectele type_info se compară cu ==/!= și expun name() (nume dependent de compilator). Particularități: pentru clase polimorfice, typeid(*p) se evaluează la rulare și dă tipul dinamic (real) al obiectului; pentru tipuri nepolimorfice dă tipul static, decis la compilare. typeid(p) (pe pointer) dă mereu tipul static al pointerului — diferența typeid(p) vs typeid(*p) e capcana clasică. Dereferențierea unui pointer nul în typeid aruncă std::bad_typeid. Motivație: identificarea tipului real într-o ierarhie polimorfică (RTTI), ex. logging, dispatch dependent de tip, verificări înainte de downcast (alternativ la dynamic_cast).

Operatorii de conversie C++

CastFolosireVerificare
static_cast<T>(e)conversii „înrudite": numerice, void*↔T*, upcast, downcast neverificatla compilare
dynamic_cast<T*>(p)downcast sigur în ierarhii polimorficela rulare: nullptr la eșec (pe pointeri), std::bad_cast (pe referințe)
const_cast<T>(e)adaugă/elimină const/volatiledoar calificative; modificarea unui obiect născut const = UB

if (D* d = dynamic_cast<D*>(p)) d->specific();   // reușește: p chiar pointează la D
B* r = new B;
D* d2 = dynamic_cast<D*>(r);                      // d2 == nullptr (eșec controlat)
D& rd = dynamic_cast<D&>(*r);                     // aruncă std::bad_cast
  • Cast-ul „C" (D*)p face conversia fără nicio verificare — în subiecte compilează (2024/I: ((D*)p)->get_j()), dar e nesigur la rulare.
  • dynamic_cast cere ca tipul sursă să fie polimorfic (măcar o funcție virtuală), altfel eroare de compilare.
Capitolul 10 · Curs 8 · întrebare de teorie: mecanismul excepțiilor (2024/V & V2-XVII) · program: 2025/VII (throw cu referință la bază)

Tratarea excepțiilor

Sintaxă și mecanism

try {
    // cod care poate eșua
    if (eroare) throw ObiectExceptie(...);   // sau throw 5; throw "mesaj";
}
catch (TipPrecis& e)  { /* primul catch compatibil ca TIP */ }
catch (Baza& e)       { /* prinde și derivatele aruncate */ }
catch (...)           { /* orice altceva */ }
  • throw expr; creează o copie a expresiei (obiectul-excepție) și pornește derularea stivei (stack unwinding): se apelează destructorii tuturor obiectelor locale construite complet, până se găsește un catch potrivit.
  • Blocurile catch se încearcă în ordinea scrierii; se alege primul al cărui tip se potrivește cu tipul static al expresiei aruncate.
  • Nu se fac conversii de tip la potrivire (un int aruncat NU e prins de catch(double)!). Singurele potriviri „largi": derivată → catch de bază (referință/pointer), și catch(...).
  • Aruncarea/prinderea nu este un apel de funcție: controlul sare direct la handler, fără adresă de retur; ce era pe stivă între throw și catch se distruge.
  • Excepțiile pot fi aruncate din funcții (oricât de adânc): dacă funcția nu le prinde, ele se propagă la apelant; dacă nimeni nu le prinde → std::terminate().
  • throw; (fără expresie) într-un catch re-aruncă excepția curentă mai departe.
  • Ordinea corectă a handler-elor: derivatele înaintea bazelor (altfel baza „mănâncă" tot); catch(...) ultimul.
📋 Răspuns model · „Mecanismul de tratare a excepțiilor" (2024/V & V2-XVII) — pe punctele de barem

0.1 sintaxă try { ... throw expr; } catch (Tip v) { ... } catch (...) { ... }.

0.1 alegerea catch-ului Se alege primul bloc catch (în ordinea textului) al cărui tip corespunde tipului expresiei aruncate.

0.1 fără conversii La potrivire nu se aplică conversii de tip (int aruncat ≠ catch(double)); excepție: o derivată e prinsă de un catch cu referință/pointer la bază.

0.1 mecanism throw/catch nu sunt apeluri de funcții: se face derularea stivei (se apelează destructorii obiectelor locale) și controlul se transferă direct handler-ului; nu există revenire la punctul lui throw.

0.1 catch(...) catch(...) prinde orice excepție (se pune ultimul). 0.1 din funcții Excepțiile aruncate în funcții se propagă către apelanți până la primul handler potrivit; ne-prinse → terminate(). Exemplu scurt: try{ f(); } catch(const char* m){ cout<<m; } catch(...){ } unde f() face throw "div 0";.

Subiectul 2025/VII — ce tip „pleacă" la throw?

class Baza{ public: virtual ~Baza(){} };
class D1 : virtual public Baza{};
class D2 : public D1{};
class D3 : virtual public Baza{};
class D4 : public D3, public D1{};
int main() {
    D4 ob;
    Baza& re = ob;          // referință la bază, dar obiectul e D4
    try{ throw re; }        // ⚠ se aruncă o COPIE de tip STATIC: Baza (slicing!)
    catch(D1& o){cout<<"D1\n";}
    catch(D2& o){cout<<"D2\n";}
    catch(D3& o){cout<<"D3\n";}
    catch(D4& o){cout<<"D4\n";}
    catch(Baza& o){cout<<"Baza\n";}
}
Baza

Explicație: throw re; copiază expresia după tipul ei static — Baza (are loc slicing, partea derivată se pierde). Un obiect Baza nu se potrivește cu catch(D1&)…catch(D4&) (conversia bază→derivată nu există), deci îl prinde catch(Baza&). Variantă de examen: dacă s-ar arunca direct throw ob; (tip static D4) cu handler-ele în ordinea D2, D3, D1, D4, l-ar prinde primul compatibil: catch(D3&) — pentru că D4 derivă din D3 — afișând „D3", nu „D4".

Excepții și constructori/destructori

  • Constructorii nu returnează valori → semnalarea eșecului se face natural prin excepții. Pentru un obiect parțial construit nu se apelează destructorul (doar destructorii membrilor/bazelor deja construite).
  • Un destructor nu trebuie să lase excepții să iasă din el (risc de terminate în timpul unui unwinding).
  • Ierarhia standard: std::exception → logic_error, runtime_error, bad_alloc (aruncată de new la eșec), bad_cast, bad_typeid; metoda what() dă mesajul.
⚠ Capcane de examen
  • throw 2; + catch(double) → NU se potrivește (fără conversii) → cade pe catch(...) dacă există, altfel terminate.
  • Tipul aruncat = tipul static al expresiei de după throw (2025/VII): referința la bază aruncă o Bază.
  • catch(Baza) prin valoare prinde derivata, dar cu slicing; corect: catch(Baza&).
  • catch-urile NU se „cumulează": se execută exact unul.
Capitolul 11 · Curs 8 · întrebare de teorie: clase template (2024/XVII & V2-V) · program: 2024/X & V2-IX (template vs non-template)

Template-uri (șabloane)

Funcții template

template <class T>            // echivalent: template <typename T>
T maxim(T a, T b) { return a > b ? a : b; }

maxim(3, 7);        // T dedus = int
maxim(2.5, 1.5);    // T dedus = double
maxim<double>(3, 7.5);   // explicit, când deducția ar fi ambiguă
  • Compilatorul generează (instanțiază) câte o funcție concretă pentru fiecare combinație de tipuri folosită — la compilare, nu la rulare.
  • Deducția cere consistență: maxim(3, 2.5) e ambiguu (T=int sau double?) → se precizează explicit.
  • La supraîncărcare template vs funcție obișnuită cu potrivire exactă, câștigă funcția obișnuită (non-template) — esența subiectului 2024/X.

Subiectul 2024/X & V2-IX

template<class X>
int functie(X *x, int y) { return x+y; }       // ar returna X* (pointer aritmetic)!
int functie(int *x, int y) { return x-y; }     // potrivire EXACTĂ pentru (int*, int)
int main() {
    int *a = new int(45), b=27;
    cout << functie(a,b);     // se alege NON-template-ul…
}
eroare de compilare: „invalid conversion from int* to int" — funcția aleasă (non-template) returnează x-y, adică un int* (aritmetică de pointeri), care nu se convertește la tipul declarat int · reparația de barem: pe linia 6 tipul funcției devine int*

Observație de barem: dacă răspunzi că eroarea e în template, primești doar parțial (0.2) — rezoluția alege non-template-ul, deci el conține eroarea raportată.

Clase template

template <class T, int N = 10>        // parametri de tip + parametri-valoare, cu default-uri
class Stiva {
    T elem[N];
    int varf;
public:
    Stiva() : varf(0) {}
    void push(const T& v);
    T pop() { return elem[--varf]; }
};
template <class T, int N>             // metodele definite în afara clasei repetă antetul template
void Stiva<T,N>::push(const T& v) { elem[varf++] = v; }

Stiva<int> s1;                // T=int, N=10 (default)
Stiva<string, 50> s2;         // instanțiere explicită — tipul COMPLET e Stiva<string,50>
📋 Răspuns model · „Clasele de tip template/șablon" (2024/XVII & V2-V) — pe punctele de barem

0.1 sintaxă template <class T> class C { ... };; instanțiere: C<int> ob; — tipul complet include argumentele (C<int> și C<double> sunt clase diferite).

0.1 toate metodele sunt template Într-o clasă template, toate metodele sunt implicit funcții template; definite în exterior, repetă antetul: template<class T> void C<T>::f(){...}.

0.1 tipuri default Parametrii pot avea valori implicite — de tip (template<class T = int>) sau constante (int N = 10); dacă nu se precizează la instanțiere, se iau cele predefinite.

0.1 utilitate Clase parametrizate de tip → refolosirea codului: o singură sursă pentru containere/algoritmi generici (vector, listă, stivă) — fundamentul STL.

0.1 exemplu clar Exemplul Stiva<T,N> de mai sus (concret, diferit de simpla sintaxă — cerință explicită de barem).

  • Instanțiere leneșă: metodele unei clase template se compilează doar dacă sunt folosite — o metodă invalidă pentru un anumit T nu dă eroare cât timp n-o apelezi.
  • Specializare: implementare dedicată pentru un tip: template<> class Stiva<bool> { ... };.
  • Parametrii non-tip (de ex. int N) trebuie să fie constante de compilare.
  • Definițiile template stau de regulă în header (compilatorul are nevoie de sursă la instanțiere).
Capitolul 12 · Curs 10 (STL)

STL: containere · iteratori · algoritmi

Cele trei componente

  • Containere — structuri de date generice (template): secvențiale (vector, list, deque, array), adaptoare (stack, queue, priority_queue), asociative ordonate (set, map, multiset, multimap — arbori roșu-negru) și neordonate (unordered_map etc. — hash).
  • Iteratori — „pointeri generalizați" care leagă algoritmii de containere: begin() / end() (end = după ultimul element). Categorii: input, output, forward, bidirecțional (list, set, map), acces aleator (vector, deque).
  • Algoritmi — #include <algorithm>: sort, find, count, copy, reverse, min_element, for_each… lucrează pe intervale [first, last) de iteratori, independent de container.
vector<int> v = {4, 1, 7};
v.push_back(9);
sort(v.begin(), v.end());
for (vector<int>::iterator it = v.begin(); it != v.end(); ++it)
    cout << *it << " ";                      // 1 4 7 9
map<string,int> note; note["POO"] = 10;      // cheie → valoare, chei unice, sortate

Legătura cu subiectul „vector push_back" (2024/XIII & V2-XVIII)

push_back(i) cu i int și constructor SimpleClass(int) ne-explicit creează un temporar prin conversie („C"), îl copiază în vector („CC"), apoi distruge temporarul („D"). La a doua inserare, vectorul realocă: copiază elementul vechi în noul bloc (al doilea „CC") și distruge copia veche — de aici secvența completă C CC D C CC CC D D D D (explicată pas cu pas în cap. 03). Morala STL: realocarea invalidează iteratorii și costă copieri; reserve(n) evită realocările.

⚠ Capcane de examen
  • end() NU e ultimul element, ci poziția de după el; *v.end() = UB.
  • map::operator[] creează cheia (cu valoare implicită) dacă lipsește — pentru căutare fără inserare: find().
  • sort cere iteratori cu acces aleator → nu merge pe list (care are metoda proprie l.sort()).
  • Containerele STL țin copii ale obiectelor — clasele cu resurse au nevoie de copy constructor corect (Rule of Three).
Capitolul 13 · Curs 12 · fundal conceptual (SOLID, șabloane de proiectare)

Design Patterns & SOLID

Principiile SOLID

  • Single Responsibility — o clasă are un singur motiv de schimbare (o singură responsabilitate).
  • Open/Closed — deschisă pentru extindere (moștenire, virtuale), închisă pentru modificare.
  • Liskov Substitution — oriunde se așteaptă o Bază, orice Derivată trebuie să funcționeze corect (fundamentul upcast-ului sigur).
  • Interface Segregation — interfețe mici, specifice; clienții nu depind de metode pe care nu le folosesc.
  • Dependency Inversion — modulele depind de abstracții (clase abstracte/interfețe), nu de implementări concrete.

Singleton (creational) — legătura cu subiectul „max N obiecte"

class Singleton {
    static Singleton* inst;          // unica instanță
    Singleton() {}                   // constructor PRIVAT
public:
    static Singleton* getInstance() {
        if (!inst) inst = new Singleton();   // alocare dinamică, la prima cerere
        return inst;
    }
};
Singleton* Singleton::inst = nullptr;

Ingredientele — constructor privat funcție statică alocare dinamică — sunt exact cele 3×0.1p din baremul 2024/XIV; generalizarea la N obiecte (contor static + refuz) e în cap. 04.

Factory Method (creational)

class Forma { public: virtual void deseneaza() = 0; virtual ~Forma(){} };
class Cerc : public Forma { public: void deseneaza() { cout<<"cerc"; } };
class Patrat : public Forma { public: void deseneaza() { cout<<"patrat"; } };
class Fabrica { public:
    static Forma* creeaza(char tip) {        // decide LA RULARE ce derivată naște
        if (tip=='c') return new Cerc;
        return new Patrat; } };
Forma* f = Fabrica::creeaza('c');  f->deseneaza();   // clientul vede doar interfața

Observer (behavioral)

Un Subiect ține o listă de Observatori (interfață cu metoda virtuală pură update()); la schimbarea stării, subiectul îi notifică pe toți (parcurge lista și apelează polimorfic update()). Decuplează sursa evenimentului de reacții — modelul butoanelor din GUI-uri.

Strategy (behavioral)

Familia de algoritmi interschimbabili în spatele unei interfețe comune (virtual int comprima(...) = 0;); contextul primește strategia (pointer la abstracție) și o poate schimba la rulare — aplicare directă a Open/Closed și Dependency Inversion.

⚠ De reținut pentru grile
  • Singleton = constructor privat + metodă statică + instanță unică (statică/dinamică).
  • Factory întoarce pointer la bază abstractă; clientul nu cunoaște clasa concretă.
  • Observer = notificare 1→mulți prin apel polimorfic; Strategy = algoritm injectat, schimbabil la rulare.
  • Toate patterns-urile de mai sus se sprijină pe funcții virtuale + clase abstracte (cap. 07).
